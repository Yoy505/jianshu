## 2. 本批实施方案（S1/S2 + A1–A3，契约先行）

原则：不改写工作一既有语义；接口契约先改 `docs/api.md` 第五部分；模型变化走新 Alembic 迁移（down_revision = `e5c9a3f7b1d8`）；每步补测试后全量回归。

### S1 授权条款先展示再确认、分用途撤回

- 新表 `steward_consent_terms`：`(purpose, version)` 唯一，`title/text/effective_at/status/created_by`。运营在后台发布新版本即成为该 purpose 当前版本；**门禁与授权都以当前版本为准**。
- C 端新增 `GET /mp/steward/consent-terms`（返回各 purpose 当前条款全文与版本，供展示确认）。
- `POST /mp/steward/consents` 增加 `version` 必填：服务端校验与当前条款一致并保存文本快照；重复确认同版本幂等返回原记录；条款升版后旧 v1 授权不再满足门禁（须重新确认），旧记录保留作历史。
- 撤回复用公共入口 `POST /mp/commerce/consents/{id}/revoke`，在 steward 用途上增加最小联动：撤销后写实例时间线 `consent_revoked` + 审计 `steward.consent.revoke`，auto 门禁即时回退（既有机制），为 B/C/E 预留「执行前查授权」的统一函数。
- 小程序 `my-service` 授权改为「查看条款全文 → 确认」两步；新增授权记录查看/撤回入口。
- 配置回退兼容：`STEWARD_*_CONSENT_TEXT` 配置文本不再直接作为授权依据（迁移到条款表；未发布条款时保持 503 待配置）。

### S2 试点放行门禁

- 新表 `steward_pilot_releases`：适用 `package_id/package_version_id`、环境（dev/staging/prod）、负责人、各项前置凭据（合同附件、供货型号、机构/医师与替补排班、签发计划、退款中断方案、值班运营、触达通道验证——结构化 `source/reference/note`，非布尔勾选）、`effective_from/effective_until`、`revoked_at/revoke_reason`。**默认无放行记录 → 激活阻断**。
- `activate_instance` 追加第十项放行门禁：存在未撤销、在有效期、覆盖该实例包版本与当前 `APP_ENV` 的放行记录，否则 409 并在缺项中列 `pilot_release`。
- 后台 API：`GET/POST /admin/steward/pilot-releases`、`POST .../{id}/revoke`（`steward.manage`），全程审计。
- 既有测试的 `full_setup` 增补「创建放行记录」步骤（测试凭据为结构化假凭据，仅测试库）。

### A1 激活凭证与排班核验

- 新表 `steward_care_plans`（个人计划签发）：`user_id/instance_id(可空,准备期签发后绑定)/physician_id/org_name/version/content(JSON)/issued_at/valid_until/revoked_at`。`physician_plan` 门禁从纯人工凭据升级为「存在有效签发计划且医师=实例签约医师」；`PrepPassIn` 人工路径保留但须引用计划 id。
- 激活时写入 `plan_version`（来自签发计划版本），任务生成沿用该版本。
- 排班强化：负责管家与替补必须为**不同** active 管家（`assign_staff` 校验 + 激活时复核）；医师须 active 且与签发计划一致。
- 新表 `steward_activation_credentials`：`instance_id` 唯一，保存本人确认时间、九项门禁判定快照、条款版本、计划版本、责任人（管家/替补/医师）、起止时间。与激活同事务写入——「preparing 草稿」与「正式激活凭证」在契约中明确区分。
- 续期：删除同人同包自动挂链；`renewed_from_instance_id` 仅由后续显式续期动作设置（本批保持 NULL，契约注明）。

### A2 暂停补时与日历一致

- `lazy_transition`：`paused` 实例**不再**按 `ends_at` 过期（计时已停止）；仅 `active` 到点过期。暂停实例的出路只有恢复或终止。
- 补时口径固定并写入契约：医师建议暂停全额补时；服务方核心中断**严格超过** 24h（≥24h+1s）全额补时；恰 24h 及不足仅记录并补交任务；用户主动暂停不补时。
- `resume_instance`：平移范围从「未来任务」改为「暂停开始日（上海日期）当天及之后的全部待办」——暂停期间滑入过去的任务一并顺延；暂停开始前已到期未完成的本人任务不顺延（用户不记录不顺延），由 A3 补录通道处理。`due_at`/`service_date`/`shifted_days` 一致更新，复评/随访序保持。
- `current_service_day`：暂停期间返回暂停开始日的服务日（计时冻结），恢复后按顺延后日历推进。

### A3 及时终止、任务门禁与结案

- 新服务函数 `lifecycle_sweep(db)`：批量处理（1）`active` 且 `ends_at<=now` → `expired`；（2）权益 `void` → `terminated` 并取消待办。注册 Celery beat 周期任务（与读路径同一套条件 UPDATE，幂等）；测试直接调服务函数验证「无人读页面也能推进」。
- `complete_user_task` 门禁：实例须 `active`（暂停/到期/终止均 409）；任务 `service_date<=今天`（未来任务 409）；历史日期补打卡须填 `backfill_reason`。
- `record_task_result`（后台）：保留到期实例上的复评/结案登记；未来日期任务须带补录字段（`actual_occurred_at` + `backfill_reason`，新列经迁移加入 `steward_tasks`）。
- `close_instance`：落地 `_open_high_priority_tickets()` 钩子（当前查 D 域工单表占位实现返回 0，D 落地后接真表）；复评完成 + 报告非空维持。
- 结果更正：任务已有结果时不再覆盖——`record_task_result` 对已完成任务返回 409（现状已如此），补录/更正走新版本结果字段（本批先落列与校验，D 域报告版本化时统一）。
