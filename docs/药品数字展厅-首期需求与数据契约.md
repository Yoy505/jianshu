# 药品数字展厅：首期需求与数据契约（R1 草案）

**状态：待项目方、数据提供方、医学审核负责人确认；不可据此宣称功能或合作已上线。** 版本：2026-09-23 / v0.1。本文是给产品、后端、小程序、B 端和测试共同执行的候选契约；带“拟”的字段、接口和权限尚未实现。页码均为 PDF 从封面起算的物理页码。项目书展示的是拟议流程，不证明药立方合同、数据许可、医师资质核验或广告审查已经完成。

## 3. 首期范围、非范围与发布层级

### 3.1 R1 最小业务范围

1. **基础资料：** 以通用名为入口，提供同名/剂型/厂家去重规则；字段最少含通用名、剂型、生产企业、OTC/处方/基药/医保标签、经核对的基本信息、科普说明、来源、版本和更新时间。标签来源与适用日期要分别记录，不以人工输入的字符串作为事实证明。
2. **C 端：** 仅检索、详情展示和收藏公开有效的版本。保留现有 `q`、`tag`、`letter`、分页及收藏接口；详情分清“药品基础资料”“企业品牌内容”“科普视频”。无获许可视频时隐藏模块，不使用空视频或未授权链接占位。
3. **内容工作流：** 草稿、提交、驳回、审核通过、发布、撤回/下架及审计留痕；待审新版本不得覆盖旧公开版。来源过期、授权终止或审核撤销可使公开内容立即不可见。
4. **B 端闭环（条件性）：** 企业主体核验、账号与企业绑定、产品认领、证明材料、品牌资料维护、提交审核、驳回修改、发布与撤回。可由药立方提供已签约接口和工作台，也可由项目方自建，二选一的责任及数据边界须先确定。
5. **医师留言（条件性）：** 仅经核验且有效的医师身份可提交；提交结果是 `pending`，只有独立审核通过后才进入可见列表。资质过期、撤销或内容下架时应停止新提交，并按规则复核既有展示。

### 3.2 R1 明确不交付

AI 医师助手、个体化用药建议/处方、药物相互作用自动判断、临床专病数据库、AI 综合比较、在线问诊、药品购买、支付、招商实时看板均不计入本期完成率。广告位/付费品牌推广只有完成广告属性和展示规则审查后另行启动；R1 的企业资料页不自动等同广告发布。8 月版第 56 页商城仍处规划状态。

### 3.3 分层发布闸门

| 层级 | 可对外的内容 | 前置条件 |
|---|---|---|
| R1a 基础展厅 | 经授权且独立审核的药品基础资料、检索、收藏 | 数据许可/来源可追溯；迁移完成；旧演示数据隔离；公开过滤、下架和回滚验收通过 |
| R1b 品牌协作 | 经核实企业认领、审核并发布的品牌内容 | B/C 主体、合同/API、安全与运维责任明确；企业隔离和证据审核通过 |
| R1c 医师留言 | 核验有效医师的已审核留言 | 医师资质制度、资料最小化保存、审核/举报/撤回流程和责任人到位 |

可分层验收；R1a 上线不应被描述为 R1b、R1c 已实现。未达到各层前置条件的入口隐藏或明确显示“暂未开放”，服务端拒绝写入。

## 4. 资料来源、版本与公开规则（拟）

**来源记录。** 每个基础资料、品牌资料、视频都要关联来源记录：`source_type`（授权数据库/公开资料/企业提交/编辑整理）、提供方、文档或接口标识、来源版本/发布日期、采集时间、授权或使用依据编号、许可范围和到期日、文件校验值。具体原件在受控存储中保存，公开端只给可披露的来源名称和“资料更新于”。合作方提供的医学数据库与视频不能因为项目书列出就直接导入；禁止把爬取数据或演示 seed 当成已授权资料。

**分层版本。** 基础资料与品牌资料分开修订、分开审核；每次提交生成不可原地改写的快照，记录 `version_no`、提交者、提交时间、差异、来源、审核人、审核意见、发布时间和撤回原因。一个药品最多有一个当前公开基础版本；同一已认领企业的品牌内容最多一个当前公开版本。视频作为有授权证明的资产挂到对应版本。编辑新稿不影响已公开旧版。

**状态机。** 候选状态：`draft → submitted → approved → published`；`submitted → rejected → draft`；`published → superseded/withdrawn/offline`。`approved` 仅表示内部审核通过，**不能在 C 端显示**；发布需单独动作。新版本发布后旧版本变为 `superseded`。`offline` 使列表、搜索、详情、收藏列表以及所有缓存中的该版本失效。回滚是重新发布一个引用旧内容的新版本并留下审核记录，不删除历史。来源授权到期/被撤销时应触发停用或人工复核；自动停用规则需与数据方确认。

**公开谓词。** `drug` 未下架、当前基础版本为 `published`、来源许可有效且该版本未撤回时才进入 C 端；品牌内容须额外满足认领有效、版本 `published` 和资产许可有效。未通过任何一条，匿名与登录用户都不能通过 ID、检索、收藏或缓存读到内容。旧表无这些字段，迁移时一律置为待审，不默认发布。

## 5. 企业认领与 B/C 责任待确认

7 月版第 25 页提出线下协议后发放企业账号，第 27–29 页展示认领、修改、提交与材料审核；8 月版第 54 页延续企业工作台。**目前仓库没有该流程，也没有可据以确认的药立方签约文件。**

| 责任项 | 候选责任分工（须书面确认） | 未确认时的处理 |
|---|---|---|
| B 端账号、企业主体和产品认领 | 北京豌豆云/药立方或其授权运营方核验企业、签协议、维护成员与认领证据；杏临汇只接收可审计的授权结果 | 不开放企业自助认领或对外显示“已认证企业” |
| 药品主数据、视频与版权 | 数据提供方列明字段、来源、许可证、更新/撤回事件、传输方式、费用及终止后的处置；杏临汇执行导入和版本映射 | 只使用项目方有权使用、可独立核实的静态子集 |
| 企业提交的品牌内容 | 企业对提交材料真实性负责；指定医学/内容审核岗核对内容与证明；发布方对展示负责 | 不显示企业品牌页或广告位 |
| C 端账号、收藏、展示与投诉 | 杏临汇运营主体管理 C 端登录、公开过滤、用户请求与投诉入口；向 B 端只共享协议允许的最小汇总数据 | 不向合作方同步 C 端身份或健康数据 |
| 接口、审计、故障和撤回 | 双方约定租户 ID 映射、接口鉴权、幂等、重放、同步延迟、下架通知、日志留存、故障处理与退出迁移 | 不把“统一后台”解释为共享数据库或管理员账号 |

**认领规则（拟）：** 企业成员只能查看和编辑本企业申请；同一品牌/批准文号的排他或多企业冲突规则由业务方确定。认领需企业证明与产品关系证明，`pending → verified/rejected/revoked`；产品基础资料不因认领自动变为企业可改。企业提交品牌版本后由非提交人审核；撤销认领立即停止其品牌内容的新发布，并按运营规则撤回现有内容。

## 6. 医师身份与留言先审后发（拟）

7 月版第 23 页写“医师留言板（需实名认证后获得权限）”，第 24 页提出分级注册与留言权限；两页**没有**给出已实施的核验服务。8 月版第 52 页延续“认证医师留言板”设想。当前 `MpProvider` 展示字段和普通 `User` 登录均不构成医师执业资质证明。

1. 建用户与执业资质的独立核验记录：真实身份核验结果、执业范围/机构、核验方式与证据引用、核验人、核验时间、有效期、撤销时间；原始证件资料仅限授权核验岗访问，公开端只显示经批准的姓名/机构/专业和核验状态。核验方式、更新频率、异议处理及可展示字段由项目法务/医学负责人确认。
2. 留言 `pending` 创建后先由医学审核岗检查关联药品、表述与来源，再由有发布权的人员批准；允许 `rejected`、`published`、`withdrawn`，不物理删除审核轨迹。提交者不能审核自己的留言。
3. 留言仅为一般专业信息交流；不得在公开板回答具体个人病情、给个人调整剂量、停药、替代处方等建议。出现此类内容应拒绝公开并引导至有资质的正规服务路径。举报、投诉和复核应产生事件记录。
4. 医师资质过期/撤销时拒绝新留言；既有已发表留言需进入复核队列，显示/撤回规则由业务方确认。**在 R1c 未验收前继续沿用当前生产/预发布 `feedback_mode="closed"` 与 503 拒绝，且不展示旧未审核留言。** 开发/测试演示不得标成真实医师或已审核。
5. 第 24 页对处方药展厅及留言板“查看权限”的版面关系不够明确。R1c 默认最严：未完成资质核验者不可读取医师板；处方药信息公开层级另作决策，不能让 C 端现有标签列表自动决定访问权限。

## 8. 最小数据模型与迁移顺序（拟）

以下为逻辑表/字段草案，字段类型和索引由实施时 Alembic 迁移确定。`*_id` 均需外键；状态、版本唯一性和“同一当前公开版”应由数据库约束及事务共同保证。

| 表或改动 | 最小字段/约束 | 用途 |
|---|---|---|
| 保留 `mp_drugs` | 现有 `id` 与检索键；新增 `catalog_status`、`current_base_revision_id`（可空）、`offline_at/reason` | 维持现有 ID/收藏兼容；旧内容字段暂保留，但不再作为公开真源 |
| 新 `mp_drug_sources` | `id, source_type, provider, source_ref, source_version, collected_at, license_ref, license_scope, license_expires_at, checksum, status` | 每份资料/视频的来源及可用性；证明文件存私有对象存储 |
| 新 `mp_drug_revisions` | `id, drug_id, content_kind(base/brand), enterprise_id?, version_no, payload, source_id, status, submitted_by, reviewed_by, reviewed_at, published_by, published_at, withdrawn_at, reason`；`(drug_id, content_kind, enterprise_id, version_no)` 唯一 | 不可改写的基础/品牌内容快照；审核人与提交人不得相同 |
| 条件性新 `mp_enterprises`, `mp_enterprise_members`, `mp_drug_claims`, `mp_drug_evidence` | 企业主体及状态；`(enterprise_id, user_id)` 唯一；认领的药品、状态、核验人/时间和 `current_brand_revision_id`；私有材料对象键和校验值 | 自建 B 端时必需；若药立方承载，改为本地最小映射与同步事件，仍须可审计 |
| 新 `mp_physician_verifications` | `user_id`、`status`、证据私有引用、执业机构/范围、`verified_by/at`、`expires_at/revoked_at`；每人最多一条当前有效记录 | 将 C 端登录用户和执业身份分开，保留历史核验；不能用 `mp_providers` 的姓名/职称代替 |
| 扩展 `mp_drugs_feedback` | `status` 默认 `legacy_unreviewed`、`physician_verification_id?`、`reviewed_by/at`、`published_at`、`withdrawn_at`、`review_reason` | 旧留言默认不可公开；新留言仅核验医师可创建，初态 `pending` |
| 复用审计日志或新增 `mp_drug_workflow_events` | `actor_type/id, enterprise_id?, target_type/id, action, before/after_status, occurred_at, request_id` | 覆盖企业、编辑、审核、发布、撤回、同步和资质撤销；只追加不覆盖 |

**迁移次序：** (1) 新增可空列/新表/索引与审计事件，现有接口继续运行；(2) 将旧 `mp_drugs` 内容快照回填为 `legacy_unreviewed`，旧留言也标此状态，**不自动发布**；(3) 获取来源证明与授权后按条审核，生成首批发布版本；(4) C 端列表、详情、收藏、后台统计统一改读公开谓词，验证旧 ID 兼容、缓存失效与下架；(5) 接入 B 端及医师流程并分别开启入口；(6) 在双读对账和回滚演练后再移除旧内容真源。必须用目标 PostgreSQL 跑迁移与回滚测试，不能只凭 SQLite `create_all` 测试通过。

## 9. API 契约草案

均以 `/api/v1` 为前缀；表中 `拟新增/拟调整` 不能视作当前可调用接口。错误语义：未登录 `401`、无角色/企业权限 `403`、不存在或非公开资源 `404`、版本冲突 `409`、字段错误 `422`、依赖流程未开放 `503`。状态变化请求须具备幂等键或 `If-Match` 版本号，后台留审计 `request_id`。

| 调用方 | 方法与路径 | 请求/响应重点 | 发布/权限规则 |
|---|---|---|---|
| C 端，拟调整 | `GET /mp/drugs?q=&tag=&letter=&page=&page_size=` | 保留现有 `Page[DrugOut]` 字段；增加 `content_version, source_display, updated_at` | 仅当前已发布且有效的基础版本；标签需来自已核对数据 |
| C 端，拟调整 | `GET /mp/drugs/{id}` | 保留 `DrugDetailOut` 兼容字段；新增 `base_version, brand_sections[], source_display, reviewed_at, video?`；将 `feedback_mode` 扩为 `closed/reviewed`（`demo` 仅开发/测试） | 未发布/下架返回 404；品牌只读已发布版本；无授权视频不返回 URL |
| C 端，拟调整 | `POST /mp/drugs/{id}/favorite`, `GET /mp/favorites` | 保留 `{favorited}` 与分页结构 | 仅已公开药品可新增收藏；下架药品从公开收藏列表消失，私有记录可保留以便恢复 |
| 医师，拟调整 | `POST /mp/drugs/{id}/feedback` | `{content}` → `202 {id,status:"pending"}` | 资质有效、入口开放才接收；不即时进入详情 `board`；否则 403/503 |
| 医师，拟新增 | `GET /mp/drugs/{id}/feedback` | 仅已发布留言的分页列表；本人待审记录另设个人查询 | 读取范围依第 6 节待决策权限；不能返回未审核内容 |
| B 端，条件性新增 | `POST /enterprise/drug-claims`；`GET /enterprise/drug-claims` | 药品 ID、企业关系、证据引用 → `pending` | 只可操作本企业；重复/冲突返回 409 |
| B 端，条件性新增 | `POST /enterprise/drugs/{id}/brand-revisions`；`POST /enterprise/brand-revisions/{revision_id}/submit` | 品牌内容、来源/证明对象键、`version_no` → `draft/submitted` | 不能修改基础资料；提交后快照不可原地变更 |
| 后台，拟新增 | `GET /admin/mp/drug-revisions?status=`；`POST /admin/mp/drug-revisions/{id}/review`；`POST /admin/mp/drug-revisions/{id}/publish`；`POST /admin/mp/drugs/{id}/offline` | 审核意见、发布/撤回原因、预期版本 | 审核/发布分权；不可自审；下架立即失效 |
| 后台，拟新增 | `GET /admin/mp/drug-claims?status=`；`POST /admin/mp/drug-claims/{id}/review` | 核验证据、批准/驳回、原因 | 企业审核岗；可撤销并联动品牌内容 |
| 后台，拟新增 | `POST /admin/mp/physician-verifications/{id}/review`；`POST /admin/mp/drug-feedback/{id}/review` | 核验/留言审核决定和原因 | 授权岗位且不可自审；审核通过后仍需明确发布动作或自动发布规则决议 |

示例公开详情增量（字段名待后端评审）：`{"id":123,"common_name":"示例药品","base_version":"3","source_display":"已授权来源名称","updated_at":"2026-09-01T00:00:00Z","brand_sections":[],"video":null,"feedback_mode":"closed","board":[]}`。示例仅说明结构，**不是实际药品资料或当前接口响应**。如果 B 端由药立方托管，上述 `/enterprise/*` 是对接语义而非必须由杏临汇暴露的公网路由；应改成签名回调/拉取适配器，并保持同样的租户隔离、状态和审计要求。

## 10. 验收用例与交付证据

| 编号 | 用例 | 必须看到的结果 |
|---|---|---|
| A1 | 无来源许可的旧 seed 药品、旧留言迁移后访问列表/ID/收藏 | 均不公开；后台显示待审；生产留言仍关闭 |
| A2 | 审核并发布一条有授权来源的基础版本 | 按通用名、标签、首字母可检索；详情字段、来源和版本一致；匿名/登录结果一致 |
| A3 | 编辑已发布药品的新版本，分别执行驳回、通过、发布 | 待审/驳回期间 C 端仍是旧版；发布后原子切换；历史可查 |
| A4 | 下架或来源许可失效 | 列表、详情、收藏与缓存同时不可公开；审计含原因、操作者和时间；可按流程恢复 |
| A5 | 两企业认领同一产品、企业 A 读/改企业 B 草稿 | 冲突规则按决策执行；跨企业访问均 403/404，不能泄露证据文件 |
| A6 | 企业提交品牌资料及证据，审核员驳回/批准/发布 | 未发布品牌绝不进入 C 端；发布只影响所属企业品牌区，不改基础资料 |
| A7 | 普通登录用户、资质待审/过期/撤销医师提交留言 | 请求拒绝且无公开副作用；开发演示内容不进入正式库 |
| A8 | 核验有效医师提交含个体化用药建议的留言 | 留言待审；审核拒绝并留原因；C 端不能读到内容 |
| A9 | 核验有效医师提交合规留言，审核员通过；提交人试图自审 | 先审后发；自审被拒；公开记录含可展示身份和发布时间 |
| A10 | 并发发布同一药品两个版本、重复回调、断网重试 | 最终只有一个当前公开基础版本；重复请求幂等；审计可对账 |
| A11 | 关闭 B 端/医师入口，或药立方对接失败 | C 端已审核静态资料可独立服务；未审核内容不降级公开；错误与告警可见 |
| A12 | 用目标 PostgreSQL 执行升级、回填、回滚与前后端契约测试 | 既有药品 ID/收藏不丢；公开过滤、权限、状态转换通过；回滚不造成未审内容泄露 |

交付证据应含：经双方确认的责任/数据授权矩阵、字段来源样本、迁移脚本与对账、权限和审核操作录像或测试记录、目标数据库验收结果、下架/回滚演练记录及上线清单。单纯“页面可点击”“测试环境 seed 可展示”不算通过。
