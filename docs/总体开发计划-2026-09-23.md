# 杏临汇全域健康项目总体开发计划

版本：2026-09-23；基线提交：`68948f9`。本计划以《杏临汇·全域健康管家服务中心项目》（2026 年 7 月，30 页）和《全域健康（全科医学康复向）商业计划书》（2026 年 8 月，60 页）为业务输入，以[代码审核与方向订正](代码质量审核与方向订正-2026-09-23.md)和[GLM 开发规范](GLM-开发规范.md)为工程输入。项目书的预算、合作资源和上线设想属于规划，不能直接当作已经取得的合同、资质或上线结果。

> 2026-09-24 补充：旧文学征文网页与公开 API 已下线，后台不再显示旧活动；历史稿件保留归档。当前作者端为[职业健康科普作品征集](2026职业健康科普作品征集-系统改造与上线计划.md)。下文涉及旧后台品牌或旧文学活动的记录仅代表当时实现，不作为现行交付范围。

## 1. 项目目标与产品边界

**目标：**建设可追溯、可审核的杏临汇 C 端入口和药品数字展厅首期服务链，逐步扩展为线上健康管家；线下全科医学康复中心、AI 医师助手和健康商城按独立条件启动。

**首期产品定义（待项目方确认）：**优先完成 7 月版第 17–29 页的药品数字展厅。C 端提供经审核的药品资料检索、展示、收藏与受控互动；B 端完成企业认领、资料提交、品牌维护和审核发布，或通过药立方合作接口完成同等流程。当前九场景、预约、咨询页面保留为受控试点，只有真实人员、排班和服务承接已验证的项目才能对外开放。

**长期蓝图：**8 月版第 30–39、50–59 页所述“线上管家 + 线下全科医学康复中心”，包含真人服务、资质管理、线下交付、标准化、AI 与展厅。8 月版第 56 页的商城仍是规划项。仓库里的征文 H5 是独立内容活动，使用隔离的用户数据和发布计划，不计入健康项目完成率。

**业务责任初稿：**两份项目书均写明北京豌豆云承接 B 端商业合作、健树科技通过小程序承接 C 端个人业务，并提出统一后台与数据交互。正式开发企业账号、药品数据库接入和跨主体数据处理前，须确认合同、数据权属、审核责任、接口维护人、费用与事故责任。技术上采用按角色和业务主体隔离的接口/审计，不以共享超级管理员或直接共库代替合作协议。

## 2. 发布版本与阶段闸门

时间是**从前置条件满足起算的工作量估算**，不是承诺上线日期；外部资质、合作签约、备案和实体场地审批不计入工程周数。若同时有 2 名可执行工程人员、1 名兼职 QA、医学内容审核人及业务负责人参与，阶段可有限并行；人员不足时按依赖顺延。

| 阶段 | 建议周期 | 可交付物 | 阶段验收 / 不满足时处理 |
|---|---:|---|---|
| G0 范围与责任确认 | 1–2 周 | 产品范围基线、B/C 责任矩阵、服务分类、数据清单、角色权限表、展厅内容来源协议、运营负责人 | 两方签署/确认责任和数据边界；明确首期是否涉及实际互联网诊疗。未确认 B 端时，展厅只能走独立审核的静态内容路径。 |
| R0 安全开发基线 | 1–3 周，可与 G0 并行 | 修复审核报告 P0；生产配置失败关闭、真实身份/状态文案、权限/私有文件治理、CI 和测试环境 | 无默认口令或开发后门；自动回复不冒充真人；无假资质/假排班/假回执；关键端到端与安全检查有实际证据。仅允许隔离演示，不对外承诺医疗服务。 |
| R1 药品数字展厅首期 | 6–10 周，G0 后起算 | 药品主数据与版本、来源/审核、C 端检索详情收藏、B 端认领与资料维护/审核或药立方集成、医师权限和留言审核、内容运营工具 | 对照 7 月版第 17–29 页逐流程验收；企业和医师权限不可混用；资料可回溯来源、版本、审核人和发布时间；广告/处方药边界形成书面结论。 |
| R2 健康管家真实服务试点 | 8–12 周，人员/机构合作明确后起算 | 真实供方入驻核验、排班/容量、预约或意向单、人工接管咨询、服务状态、评价投诉、最小化健康档案与同意 | 逐单可查人员、服务主体、时间、价格、执行记录；并发预约不超卖；健康信息只对授权岗位可见；线下 SOP、异常/退款流程经过运营演练。 |
| R3 线下中心与标准化 | 独立立项，不给纯软件完工日期 | 场地、机构/人员资质、设备、服务 SOP、质量安全、事故处理、收费和数据对接；软件按已批准流程实现 | 实体运营主体和责任人签收；现场试运行及质量安全验收通过。小程序上线不能替代实体中心验收。 |
| R4 AI 与商城受控试点 | 独立立项，R1/R2 数据治理后 | AI 知识来源、模型评测/人工复核/转诊；商城经营主体、商品准入、交易/售后、专项广告审查 | 真实样本评测、安全事件处置、医疗/药品/广告资质与类目审查通过；未过关保持关闭。 |

`docs/launch-plan.md` 与 `docs/schedule.md` 中 2026-11-01“全端正式上线”保留为历史目标；是否能在该日发布任何范围，以相应版本闸门实际通过为准。

## 3. 工作包与依赖顺序

| 编号 | 工作包 | 核心任务 | 依赖 | 可验证完成标准 |
|---|---|---|---|---|
| F0 | 工程与发布底座 | 环境隔离、密钥校验、独立生产初始化、真实短信/微信配置、CI、迁移、备份恢复、监控、回滚 | 无 | 测试环境能从空库迁移并完成冒烟；错误配置拒绝启动；恢复演练记录可查。 |
| F1 | 身份、权限与数据治理 | B 企业、C 用户、执业人员、审核员分别建身份与权限；敏感健康数据目的/同意/保留/导出；跨主体接口协议 | G0 责任矩阵 | 越权与跨账号测试通过；公开接口不泄露健康资料或匿名身份；操作有审计。 |
| F2 | 展厅数据与内容审核 | 通用名/剂型/生产企业/标签等主数据；来源、版本、有效期；科普与品牌内容分层；审核、撤回、下架、纠错 | 药立方数据授权及医学编辑 | 每条公开信息能追溯来源、变更与审核；撤回可生效；示例数据不会误标为真实。 |
| F3 | 展厅 C 端 | 搜索、分类、详情、收藏、科普视频/资讯、受控留言；异常与无数据状态 | F1、F2 | 真机逐页验收；与 API 契约一致；处方药和广告展示按审核结论控制。 |
| F4 | B 端企业流程/集成 | 企业账号、产品认领、品牌维护、证据材料、提交/驳回/发布、审计；如药立方提供则改为合同 API | G0 与 F1、F2 | 用真实企业测试账号完成认领→审核→发布→C 端展示；未经审核内容不可公开。 |
| F5 | 医师互动权限 | 实名与执业资质核验、角色授权、留言审核/举报/撤回、有效期复核 | F1、机构/人员审核方案 | 普通用户无法以医师身份留言；已过期/撤销资质立即失权。 |
| F6 | 健康服务交付 | 供方入驻、资质、排班、容量、预约/意向、人工咨询、服务完成与评价、投诉 | G0 医疗边界、F0/F1 | 展示与下单同一排班；真实人员回复有身份和时间；并发、取消、封禁与异常路径通过。 |
| F7 | 隐私与健康档案 | 最小字段、单独同意记录、访问/更正/撤回/删除、运营岗最小权限 | G0 处理目的、F1 | 完成数据清单与影响评估；用户操作和后台权限测试通过。 |
| F8 | 实体/AI/商城扩展 | 线下中心 SOP/系统接口；AI 安全评测；商品/交易资质与售后 | R1/R2 结果、专项审批 | 每个模块独立立项、独立验收；默认关闭。 |

**关键路径：**业务责任/内容来源协议 → 身份权限与数据治理 → 展厅主数据/审核 → B 端认领发布 → C 端真实展示。健康管家的关键路径另为机构与人员合作 → 资质核验 → 排班/服务 SOP → 预约/人工咨询 → 真实试点。备案和证书只解决网络发布条件，不能替代以上业务验收。

R1 的候选字段、状态机、角色权限、接口和 12 条验收用例见[药品数字展厅首期需求与数据契约](药品数字展厅-首期需求与数据契约.md)。该文档是待确认设计，药立方授权、B 端责任与医师核验结论未取得前不能据此开放对应能力。

按阻断程度排序，任务可分开提交，但同一业务不变量必须端到端完成。状态只写本次可核对的事实，不能提前标记“完成”。

| 顺序 | 任务 | 本次行动 / 验收 |

## 5. 研发与交付规则

- GLM 每项任务先按[开发规范](GLM-开发规范.md)定位源码、核对 Git 状态、提交变更范围与验收方案。接口变化同步 `docs/api.md`；表结构变化同步 Alembic 迁移，不在生产运行 `create_all` 或演示 seed。
- 每项任务的完成定义：有可复现的实际行为、权限和失败路径；关键变更有适当自动化测试；小程序页面在模拟器或真机可见；后台/H5 构建及后端迁移/测试在可用环境运行；交付记录明确未验证的外部依赖。
- 保留独立开发、测试、生产环境。生产服务默认关闭未验收功能；演示数据、模拟消息和固定凭据不得进入真实环境。所有上线闸门按模块签收，不以“所有页面看起来完整”代替。
- 未取得医疗机构和人员的相应资质及合作协议前，界面只描述健康信息、服务协助或预约意向；不把免责声明当作诊疗许可。医疗健康信息属于敏感个人信息，处理范围需遵循[个人信息保护法](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)；诊疗和 AI 的角色边界参考[互联网诊疗监管细则](https://www.nhc.gov.cn/yzygj/c100068/202203/2072f0e8988249e59d942e1b2a933916.shtml)。

## 6. 资源、预算与风险

8 月版第 59 页的 I 期 500 万元分为线下样板 320 万、标准化 50 万、AI 助手 80 万、药品展厅 50 万；这是项目书估算，不是当前仓库的工程预算或已落实资金。建议按上述版本设置独立预算包，并在每次立项前补齐报价、合同、负责人、收益与退出条件。R1 展厅与 R3 线下中心不应共用一个“软件已完成”验收结论。

用户规模口径也需订正：7 月版第 14 页以“10 万级用户”论证，8 月版第 35、43 页出现“40 万+”规划。两者均不应直接作为现网流量或采购规格；G0 应由运营提供可核对的获客、活跃、峰值与留存假设，R1 再按压测结果决定容量和费用。

| 风险 | 触发信号 | 控制措施 |
|---|---|---|
| B 端数据/合作未落实 | 无数据库授权、无企业审核人或接口合同 | R1 缩为独立审核的有限科普内容，不宣称完成企业闭环。 |
| 医疗服务边界不清 | UI 用“医师在线诊疗”等词，但无机构资质与真人服务 | 先关闭或改准确文案；诊疗模块单独评审与验收。 |
| 健康数据跨主体扩散 | 统一后台可查看所有档案与会话 | 目的限定、角色/租户隔离、单独同意和访问审计。 |
| 演示能力被误当真实业务 | 假资质、假排班、假短信、自动回复 | 生产配置失败关闭；所有承诺由服务端状态和外部回执驱动。 |
| 过早固定上线日期 | 备案、内容/资质/测试闸门未过 | 分模块发布；日期服从验收结果。 |
| 单机部署与实时通道不匹配 | 多 worker 下丢消息、无恢复演练 | 共享消息通道、队列/监控、恢复和回滚演练。 |
| 用户规模与成本假设未统一 | 10 万级与 40 万+目标并存、缺少真实峰值 | 统一指标口径，先做小规模试点与压测，再决定扩容预算。 |

## 7. 待项目方确认的决策

1. 首期对外发布是否按**药品数字展厅优先**执行；若希望同时开放预约，需确认真实服务人员和履约团队。
2. 首期是否限于**健康信息、服务咨询与预约意向**；实际互联网诊疗应由明确的有资质医疗机构主导，并单列病历/处方与监管方案。
3. 药立方数据库、企业工作台、B 端审核与费用由哪方交付；以书面合作责任矩阵替代代码假设。

在这些决策未定时，可以继续完成 R0 的安全与真实性修复，以及 F2 的数据/审核结构设计；真实 B 端账号开放、医疗诊疗、收费交易和跨主体健康数据共享不得凭项目书文字直接上线。

**本次验证：**本机 Python 3.12 虚拟环境的后端全量测试 `44 passed`，另有 3 条第三方弃用/SQLite 连接清理警告；管理后台 TypeScript/Vite 构建通过但仍提示约 1.08 MB 主包；小程序全部 WXML 由微信编译器通过，全部 JavaScript 通过 `node --check`，JSON 解析与 `git diff --check` 通过。WS 封禁、公开环境拒写、私有导出和聊天帧隔离有针对性测试。尚未在微信真机、目标 PostgreSQL/Redis、真实短信和服务器部署环境做端到端验收。

**下一开发批次（R0 尚未完成）：**先实现真实短信与安全的首次管理员开通；再落实敏感健康信息单独同意/撤回删除、人员资质核验、真实排班和并发约束；并完成药品来源/审核迁移、文件与跨进程消息治理。每项独立按第 2 节闸门验收。R1a 展厅可在数据授权与医学审核责任明确后开始实体开发；R1b 企业认领和 R1c 医师留言仍依赖第 7 节决策。
